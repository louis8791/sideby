## MVP 產品說明、ASCII UI、技術規格與系統架構

> 文件範圍：只描述本次可實作、可展示的 MVP。  
> 已排除 CRM、商家管理後台、App 內付款、訂閱制度、社群、遊戲化、驚喜約會、全臺擴張與未來產品藍圖。

# 1. 產品說明

## 1.1 一句話產品

> **情侶只要分別說出想要的感覺、限制與地雷，AI 就在不暴露私密需求的前提下，替兩人排出三套可直接出發的完整約會行程。**

## 1.2 產品定位

本產品不是餐廳清單、景點搜尋器，也不是單純的 AI 行程產生器。

它處理的是情侶共同決策：

- 兩人的喜好不完全相同。
- 有些要求適合共同討論，有些需求不方便直接說。
- 「明亮、可愛、浪漫、放鬆、不要太正式」等條件高度主觀。
- 找到地點後，仍須處理營業時間、交通、預算、停留時間與行程順序。
- 一方不喜歡某一站時，不應整份行程全部重做。

因此，MVP 的核心是：

> **雙人私密需求整合＋主觀形容詞敏感度學習＋完整可執行行程生成＋共同修正。**

## 1.3 目標使用者

- 居住或活動於大臺北地區的情侶。
- 主要為大學生及 20～30 歲年輕使用者。
- 想臨時出門，或提前規劃半日／一日約會。
- 願意讓 AI 協助處理雙方偏好，但不希望所有個人想法都直接暴露給另一半。

## 1.4 核心使用情境

### 情境 A：現在就出發

兩人臨時想約會，輸入：

- 當下或集合位置
- 可用時間
- 預算
- 交通方式
- 今天想要的氣氛
- 個人不方便直接說的要求

AI 在短時間內排出三條目前可執行的完整路線。

### 情境 B：規劃未來約會

兩人指定日期與時間，AI 可納入：

- 預約型餐廳或活動
- 電影、展覽、手作、運動、娛樂
- 餐飲、活動、散步或景點的完整順序
- 所有站點之間的交通與停留時間

## 1.5 MVP 產品承諾

價值優先順序如下：

1. **從不知道做什麼，到直接出發。**
2. **理解這一對情侶，而不只是理解單一使用者。**
3. **增加約會的新鮮感。**
4. **減少搜尋、討論與安排時間。**

## 1.6 地理與內容範圍

### 地理範圍

- 臺北市
- 新北市
- 以捷運及大眾運輸可合理到達區域為主

### 行程可包含

- 餐廳
- 咖啡廳
- 甜點
- 電影
- 展覽
- 手作體驗
- 運動
- 娛樂活動
- 散步
- 景點

### MVP 不包含

- 住宿
- SPA
- 酒吧及夜生活
- 過夜行程
- 長途旅遊
- App 內付款

# 2. 使用者角色與資料可見性

## 2.1 使用者角色

MVP 只有兩個正式角色：

- **Partner A**
- **Partner B**

商家不是系統使用者；商家資料與優惠由預先建立的資料庫提供，不製作 CRM 或商家後台。

## 2.2 公開條件

兩人都可以看見並共同編輯：

- 現在出發／未來日期
- 開始時間與最晚結束時間
- 集合地點
- 兩人總預算或每人預算
- 理想預算與絕對上限
- 可接受交通方式
- 行程長度
- 是否接受戶外活動
- 是否需要可立即訂位或購票

## 2.3 私密條件

每位使用者可分別輸入：

- 今天的心情與體力
- 想要的氣氛
- 不想去的類型
- 不方便直接告訴另一半的需求
- 對特定形容詞的主觀標準
- 本次是否願意配合某類活動

每筆個人輸入可設定：

- `shared`：另一半可看見
- `private_session`：只有 AI 可用，僅限本次
- `private_remembered`：只有 AI 可用，並可納入個人長期偏好

預設為：

> **私密輸入不得出現在另一半可取得的 API 回應、畫面或紀錄中。**

# 3. 核心使用流程

```text
建立雙人約會房間
        ↓
兩人進入同一 Session
        ↓
共同填寫日期、時間、預算、地點、交通
        ↓
各自在自己的手機輸入個人偏好與私密需求
        ↓
AI 將自然語言轉成結構化條件
        ↓
硬限制過濾不合格商家與活動
        ↓
情侶偏好與形容詞敏感度計算
        ↓
生成三套完整且可執行的約會行程
        ↓
兩人分別喜歡／拒絕／指出要修改的站點
        ↓
AI 保留已接受部分，局部重排衝突部分
        ↓
兩人選定最終行程
        ↓
查看合作優惠、商家詳情、外部訂位或購票
        ↓
約會後各自評分，更新偏好模型
```

# 5. 功能規格

| 編號 | 功能 | MVP 規格 |
|---|---|---|
| FR-01 | 雙人房間 | 可建立邀請碼／分享連結，兩支裝置加入同一 Session。 |
| FR-02 | 即時同步 | 公開條件、完成狀態、投票與最終方案在雙方裝置同步。 |
| FR-03 | 兩種規劃模式 | 支援「現在就出發」與「規劃未來」。 |
| FR-04 | 共同條件 | 日期、時間、集合地點、預算、交通與行程長度可共同設定。 |
| FR-05 | 私密輸入 | 個人文字與標籤可設共享、僅本次私密、私密且記住。 |
| FR-06 | 自然語言解析 | 將「明亮但不要太網美」等語句轉成可計算條件。 |
| FR-07 | 硬限制過濾 | 過敏、禁忌、預算上限、時間、交通、營業狀態不得違反。 |
| FR-08 | 三套完整行程 | 每套含多站、順序、移動、停留、價格與推薦理由。 |
| FR-09 | 雙人意見 | 雙方可喜歡／拒絕整套或個別站點，並輸入修改語句。 |
| FR-10 | 局部重排 | 保留雙方接受的站點，只替換衝突部分並重新驗證。 |
| FR-11 | 本次學習 | 對話中的「太暗、太幼稚、太累」立即影響下一輪。 |
| FR-12 | 長期偏好 | 經使用者允許後，將形容詞敏感度與回饋存入個人模型。 |
| FR-13 | 隱私轉譯 | 私密需求只影響排序，不得原句或可反推形式揭露。 |
| FR-14 | 合作方案 | 可顯示優惠、商家詳情與外部訂位／購票連結。 |
| FR-15 | 贊助治理 | 贊助不得進入適合度分數；合作內容必須清楚標示。 |
| FR-16 | 約會後回饋 | 雙方各自評分、選擇喜歡／不喜歡的站點與原因。 |

# 6. 硬限制規格

以下條件在計分前先驗證，任一項不合格即排除：

1. 日期與時間範圍。
2. 最晚結束時間。
3. 絕對預算上限。
4. 商家營業與活動入場時間。
5. 可用票券或預約狀態；無法確認時必須標示。
6. 使用者可接受的交通方式。
7. 單段與總移動時間上限。
8. 食物過敏、飲食禁忌與健康限制。
9. 無障礙及體力限制。
10. 年齡、身分或場域限制。
11. 使用者明確設定的 Hard No。
12. 戶外活動對天氣的必要條件。

```text
硬限制通過
    ↓
才進入偏好與形容詞計分
    ↓
再進入完整行程組合
```

AI 不得以「整體看起來很適合」覆蓋任何硬限制。

# 7. 主觀形容詞敏感度模型

## 7.1 目標

系統不能只辨識使用者喜歡「咖啡廳」，還要學會：

- 使用者口中的「明亮」需要多亮。
- 「可愛」的接受範圍到哪裡。
- 「浪漫」是否代表正式、安靜、夜景或儀式感。
- 「放鬆」是否代表少走路、低噪音、少排隊或低行程密度。
- 「不要太幼稚」是哪一項特徵的上限。

## 7.2 形容詞結構

每位使用者對每個形容詞保存：

```json
{
  "adjective": "cute",
  "target_min": 0.45,
  "target_max": 0.72,
  "importance": 0.80,
  "confidence": 0.65,
  "scope": "long_term",
  "source": "conversation_feedback"
}
```

欄位意義：

- `target_min`：低於此值可能不符合。
- `target_max`：高於此值可能過度。
- `importance`：這個特徵對本次或長期有多重要。
- `confidence`：系統對偏好判斷的可信度。
- `scope`：本次或長期。
- `source`：問卷、對話、選擇或約會後回饋。

## 7.3 商家主觀屬性

MVP 的真實商家資料由團隊人工標記：

```json
{
  "venue_id": "venue_023",
  "bright": 0.88,
  "cute": 0.58,
  "childish": 0.18,
  "quiet": 0.72,
  "romantic": 0.55,
  "formal": 0.25,
  "interactive": 0.20,
  "relaxing": 0.78
}
```

MVP 不依賴自動抓取大量評論或照片訓練。

## 7.4 語句解析示例

輸入：

> 想找明亮一點的咖啡廳，可愛但不要太幼稚。

解析：

```json
{
  "desired": [
    {"attribute": "bright", "min": 0.70, "importance": 0.85},
    {"attribute": "cute", "min": 0.45, "max": 0.75, "importance": 0.65}
  ],
  "avoid": [
    {"attribute": "childish", "max": 0.30, "importance": 0.90}
  ]
}
```

## 7.5 本次即時學習

使用者說：

- 「這間太暗」  
  → 提高 `bright.target_min`。
- 「這個太可愛，像親子餐廳」  
  → 降低 `cute.target_max`，並降低 `childish.target_max`。
- 「這個剛好」  
  → 提高該區間的 `confidence`。
- 「今天不想太安靜」  
  → 只修改本次 Session，不直接改寫長期偏好。

## 7.6 MVP 的模型形式

MVP 不在執行期間重新訓練大型語言模型。

採用兩層設計：

1. **LLM 結構化解析器**  
   將自然語言解析為形容詞、強度、上下限、否定、情境與隱私層級。

2. **可學習的個人敏感度模型**  
   使用數值化區間與權重，根據選擇、拒絕與回饋做線上更新。

這樣可以清楚展示「模型正在學習」，同時保持結果可測試、可控制。

# 8. 推薦與行程生成規格

## 8.1 候選資料來源

MVP 的主資料來源：

- 團隊建立的大臺北真實商家／活動資料集。
- 每筆資料包含名稱、座標、價格、營業時間、類型、停留時間、主觀屬性及外部連結。
- 合作優惠可為比賽用模擬資料，但必須明確標示。

可選擇啟用地點／路線 API 補充：

- 即時營業資訊
- 路線時間
- 地圖顯示
- 地點詳情

核心 Demo 不得依賴外部 API 才能完成；API 無法使用時，改用預先建立的資料與交通矩陣。

## 8.2 候選過濾

```text
所有場地
  ↓ 地區
大臺北候選
  ↓ 類型
符合本次行程類型
  ↓ 硬限制
時間／預算／交通／禁忌通過
  ↓ 個人適配
A 與 B 分別計分
  ↓ 情侶適配
保護較不滿意的一方
  ↓ 路線組合
產生可執行完整行程
```

## 8.3 個人適配分數

對使用者 `u` 與場地 `v`：

```text
UserFit(u, v)
= Σ〔形容詞符合度 × 重要性 × 信心值〕
  ÷ Σ〔重要性 × 信心值〕
```

形容詞符合度：

- 落在理想區間：1
- 稍微超出：依距離遞減
- 違反強烈排斥：0
- 違反 Hard No：直接排除，不進入計分

## 8.4 情侶方案分數

所有硬限制通過後：

```text
CoupleScore
= 45% × min(A 適配度, B 適配度)
+ 25% × mean(A 適配度, B 適配度)
+ 15% × 本次情境符合度
+ 10% × 新鮮感
+  5% × 路線效率
```

使用 `min(A, B)` 作為最高權重，是為避免：

```text
A = 100 分
B =   0 分
平均仍有 50 分
```

贊助與合作費用不得加入 `CoupleScore`。

## 8.5 完整行程生成

每套行程必須包含：

- 集合時間與地點
- 2～4 個站點
- 每站抵達與離開時間
- 站點間交通方式與時間
- 每站預估花費
- 總預算
- 總行程長度
- 商家營業或活動時段驗證
- 可安全公開的推薦理由
- 合作優惠標示
- 外部訂位或購票連結

## 8.6 三套方案的多樣性

三套方案應至少符合其中兩項：

- 不同主要活動類型
- 不同氣氛
- 不同預算層級
- 不同區域
- 不同移動密度

任兩套方案不得有超過 50% 的相同站點。

## 8.7 找不到完美交集

系統依序處理：

1. 不放寬任何硬限制。
2. 找到雙方都可接受的方案。
3. 產生「一站偏向某方、另一站平衡另一方」的組合。
4. 參考前次偏好權重進行輪替，但不得揭露誰正在配合誰。
5. 若仍無可行方案，明確表示無法同時滿足，要求使用者選擇可放寬的軟條件。

# 9. 私密需求轉譯規格

## 9.1 基本原則

私密輸入：

- 可以影響篩選、排序與重排。
- 不可原句回傳。
- 不可顯示輸入者。
- 不可用足以推測輸入者的方式解釋。
- 不可寫入對方可查詢的歷史紀錄。

## 9.2 安全輸出示例

私密輸入：

> 我不想又陪他去拉麵店。

禁止輸出：

> A 不想再陪 B 吃拉麵。

禁止輸出：

> 其中一方不想吃拉麵。

允許輸出：

> 本次提高了料理多樣性與新鮮感的權重。

或不提供任何排除原因，只顯示最終方案。

## 9.3 Privacy Guard

所有對雙方共同顯示的文字，送出前必須經過 Privacy Guard：

```text
LLM 生成說明
    ↓
檢查是否含私密原句
    ↓
檢查是否含身分指向
    ↓
檢查是否能反推私密偏好
    ↓
改寫為共同條件或中性理由
    ↓
才可回傳前端
```

# 13. 後端模組責任

## 13.1 Natural Language Parser

輸入：

- 原始文字
- 使用者既有偏好
- 本次情境

輸出固定 JSON：

- 硬限制
- 軟偏好
- 形容詞與強度
- 否定條件
- 本次／長期範圍
- 可否共享

## 13.2 Hard Constraint Filter

- 使用純程式規則。
- 不允許 LLM 自行決定是否忽略限制。
- 回傳每個候選的通過／淘汰原因。

## 13.3 Adjective Sensitivity Engine

- 計算個人對主觀屬性的理想區間。
- 處理「不夠、太過、剛好」等相對回饋。
- 支援本次更新與經同意後的長期更新。

## 13.4 Couple Scoring Engine

- 分別計算 A、B 的適配度。
- 以較低一方作高權重。
- 不納入贊助因素。
- 輸出可供行程組合的候選分數。

## 13.5 Itinerary Composer

- 選擇 2～4 個站點。
- 排定順序與時間。
- 驗證交通、營業、預算與停留時間。
- 產生三套具有差異的完整方案。

## 13.6 Local Replanner

- 鎖定雙方接受的站點。
- 只替換被拒絕站點。
- 重新計算後續到達時間與總成本。
- 若替換造成硬限制違反，整條修改提案作廢。

## 13.7 Privacy Guard

- 接收私密輸入摘要與 LLM 生成文字。
- 移除可識別輸入者的線索。
- 只輸出共同、安全、中性的說明。

```text
[共同條件 + A 私密輸入 + B 私密輸入]
                    │
                    ▼
         自然語言結構化解析
                    │
                    ▼
        建立本次個人偏好向量
                    │
                    ▼
       硬限制過濾場地與活動
                    │
                    ▼
         A / B 個人適配計分
                    │
                    ▼
          情侶適配與公平計分
                    │
                    ▼
      組合站點、路線、時間、預算
                    │
                    ▼

                    │
                    ▼

                    │

```

# 15. 非功能規格

## 15.1 效能

- 雙方公開狀態同步：目標 2 秒內。
- 第一輪三套行程：目標 15 秒內。
- 局部重排：目標 8 秒內。
- 外部 API 逾時後自動使用本地資料。

## 15.2 可用性

- 主要流程適用手機直向畫面。
- 每一階段只呈現當下必要欄位。
- 私密輸入畫面必須明確標示可見範圍。
- 產生中需顯示目前階段，不讓使用者誤以為畫面卡住。

## 15.3 隱私

- Partner A 與 B 的私密資料以資料列權限隔離。
- 原始私密文字不寫入共用快取與前端狀態。
- 位置資料預設只保留於本次 Session。
- 長期偏好寫入前必須取得使用者同意。
- 伺服器日誌僅記錄 ID 與錯誤類型，不記錄私密原文。

## 15.4 可解釋性

每套行程需說明：

- 符合哪些共同需求
- 預算與時間概況
- 為何適合本次情境

但不得揭露：

- 私密需求原句
- 輸入者身分
- 足以反推私密內容的拒絕理由

## 15.5 防止幻覺

- 場地只能引用資料庫中的 `venue_id`。
- LLM 不得自行創造商家、價格、營業時間或優惠。
- LLM 輸出使用固定 JSON Schema。
- 後端必須再次驗證所有時間、成本與路線。
- 驗證失敗的方案不得傳給前端。

# 16. MVP 驗收標準

## AC-01｜兩支手機加入

Partner A、Partner B 能以邀請碼進入同一房間，且看見對方在線狀態。

## AC-02｜公開條件同步

任一方修改時間、預算或交通方式，另一方 2 秒內看見更新。

## AC-03｜私密內容隔離

A 無法透過畫面、API 或 Realtime 訊息取得 B 的私密輸入。

## AC-04｜形容詞解析

系統能將：

> 明亮、可愛但不要太幼稚、不要走太多路

轉成可計算的結構化條件。

## AC-05｜完整三套行程

系統產生三套多站式完整行程，而非三個單一地點。

## AC-06｜硬限制零違反

三套方案都不能超過預算上限、最晚時間或使用者禁忌。

## AC-07｜雙人適配

推薦不能只高度符合其中一方；較低一方的適配度必須達最低門檻。

## AC-08｜局部重排

一方拒絕某站後，系統保留已接受站點，只替換必要部分。

## AC-09｜溝通中學習

使用者表示「太暗」後，下一輪方案的明亮屬性需明顯提高。

## AC-10｜不暴露隱藏需求

共同推薦理由不得顯示私密輸入者、原句或可反推內容。

## AC-11｜合作內容透明

合作方案清楚標示，且非合作方案仍可正常出現。

## AC-12｜外部行動

使用者能從最終行程開啟商家詳情及外部訂位／購票頁。

## AC-13｜約會後學習

雙方送出評分後，經同意的形容詞與活動偏好會更新個人模型。
